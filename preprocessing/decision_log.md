## Complete Preprocessing & Feature Engineering Decision Matrix

This decision log documents every design choice, trade-off, and empirical justification made across all preprocessing and feature engineering steps in the notebook.

| Step / Pipeline Phase | Decision Area | Options Considered | Chosen Option | Reason (Why We Chose / Rejected) | Empirical Evidence |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Problem Formulation** | Target Binary Definition | 1) Multi-class (`<30`, `>30`, `NO`). <br>2) Binary classification: Acute `<30` (`1`) vs `NO` + `>30` (`0`). | **Binary: `<30` (`1`) vs `NO` + `>30` (`0`)** | *Rejected 1:* Non-actionable clinical ambiguity between long-term return (>30) and non-return. <br>*Chose 2:* Aligns directly with CMS HRRP hospital penalties; focuses model capacity strictly on acute post-discharge deterioration. | Positive class rate = 11.49% (train: 9,004 vs 69,327). |
| **Step 1: Data Ingestion** | Raw Schema & Placeholder Recognition | 1) Assume `isnull()` catches all missing data. <br>2) Map explicit string placeholders (`'?'`, `'Unknown/Invalid'`, `'NULL'`). | **Map explicit string placeholders to NaN** | *Rejected 1:* Standard `isnull()` reports 0 missing values because placeholders are ingested as raw strings. <br>*Chose 2:* Accurately identifies hidden data absence. | Missing % plot (`missing_values.png`); `weight` (97%), `medical_specialty` (49%), `payer_code` (40%). |
| **Step 2: Duplicate Audit** | Exact Row Duplicates | 1) Skip duplicate check. <br>2) Explicit `drop_duplicates()`. | **Explicit `drop_duplicates()`** | *Rejected 1:* Assumes data hygiene without verification. <br>*Chose 2:* Guarantees exact duplicate rows cannot artificially inflate model confidence. | 0 duplicate rows detected in 101,766 records. |
| **Step 3b: Terminal Exclusion** | Hospice & Expired Patients | 1) Retain all rows. <br>2) Exclude terminal discharge disposition codes (11, 13, 14, 19, 20, 21). | **Drop terminal codes (2,423 encounters)** | *Rejected 1:* Severe conceptual leakage — deceased patients cannot physically be readmitted within 30 days, causing false negative inflation. <br>*Chose 2:* Restricts training cohort to viable at-risk candidates. | 2,423 encounters dropped ($101,766 \to 99,343$ encounters; `phase1_terminal_drop.png`). |
| **Step 3c: Hidden Null IDs** | Administrative Missing Code Mapping | 1) Treat ID codes 5, 6, 8 etc. as genuine categories. <br>2) Remap known missing IDs to `NaN`. | **Remap null IDs to `NaN`** | *Rejected 1:* IDs like 5, 6, 8 mean "NULL", "Unknown", or "Not Available" in `IDS_mapping.csv`. <br>*Chose 2:* Standardizes administrative missingness with medical missingness. | Mapped to `NaN` before systematic imputation. |
| **Step 3d: Informative Imputation** | High-Missing Administrative & Clinical Features | 1) Mode / Mean imputation. <br>2) Impute as distinct `"Unknown"` category. | **Impute as `"Unknown"`** | *Rejected 1:* Falsely assumes missing at random; distorts true distribution toward dominant classes. <br>*Chose 2:* Missingness in `payer_code` or `medical_specialty` is an informative clinical signal (e.g., lack of specialized referral). | Missingness remains stable without biasing existing classes. |
| **Step 3e: Test Imputation** | Glycemic Test Results (`max_glu_serum`, `A1Cresult`) | 1) Drop unmeasured encounters. <br>2) Impute as `"Not tested"`. | **Impute as `"Not tested"`** | *Rejected 1:* Drops >80% of dataset records. <br>*Chose 2:* Untested glycemic status conveys distinct clinical decision context (e.g., patient was not treated as acute diabetic crisis). | Encoded as separate valid ordinal category. |
| **Step 3f: Critical Row Pruning** | Missing Primary Diagnoses or Gender | 1) Mode-impute primary medical diagnoses. <br>2) Drop rows with missing critical fields. | **Drop rows missing critical fields (1,521 encounters / 1.5%)** | *Rejected 1:* Imputing primary diagnoses guesses the patient's core medical reason for admission. <br>*Chose 2:* Safely removes corrupted or incomplete clinical records ($99,343 \to 97,822$). | 1,521 rows dropped (1.5% of cohort). |
| **Step 4: Type Normalization** | Administrative IDs vs. Numeric Counts | 1) Leave integer ID columns as numeric. <br>2) Cast administrative IDs to `object`; verify count features are `int64`. | **Cast IDs to `object`; verify counts as `int64`** | *Rejected 1:* Numeric operations on IDs (e.g., scaling or ordering) treat arbitrary administrative codes as continuous quantities. <br>*Chose 2:* Prevents false numeric relationships during scaling. Count columns verified already `int64`. | `df_clean[col].astype(str)` for `admission_type_id`, `discharge_disposition_id`, `admission_source_id`. |
| **Step 5: Validity Checks** | Impossible Clinical Values | 1) Assume values are valid. <br>2) Explicitly verify binary gender categories and check for negative count values. | **Explicit validity checks** | *Rejected 1:* Risks silent corrupted records entering models. <br>*Chose 2:* Confirms cohort has only 'Male'/'Female' and zero negative values across medical count columns. | Filter checks confirmed 0 non-binary rows and 0 negative values. |
| **Step 6: Column Pruning** | Identifiers, Constants, and Unusable Features | 1) Keep all columns. <br>2) Drop `encounter_id`, `weight`, constant meds (`examide`, `citoglipton`), and `_desc` columns. | **Drop identifiers, constants, and `weight`** | *Rejected 1:* `encounter_id` causes memorization; `weight` is 97% missing; constant meds carry 0 variance. <br>*Chose 2:* Clean feature set without noise or leakage. | Dropped `weight`, `examide`, `citoglipton`, `encounter_id`, and redundant `_desc` mappings. |
| **Step 7: Train-Test Splitting** | Data Leakage Prevention | 1) Standard random row-level split. <br>2) Patient-grouped stratified split on `patient_nbr` (Option A: retain all visits). <br>3) First-visit only (Option B). | **Option A: Patient-grouped stratified split (80/20)** | *Rejected 1:* Severe data leakage — multiple visits from the same patient appear in both train and test. <br>*Rejected 3:* Discards ~28k valuable readmission-prone patient encounters. <br>*Chose 2:* Strict patient isolation with zero overlap while retaining complete encounter history. | Train: 78,331 encounters (55,108 patients); Test: 19,491 encounters (13,777 patients); Overlap = 0 (`phase2_split_stratification.png`). |
| **Step 8: Outlier Policy** | Right-Skewed Utilization Features | 1) Truncate / remove IQR outliers. <br>2) Retain high-utilizers; handle scaling robustly. | **Retain high-utilizers; use `RobustScaler`** | *Rejected 1:* High-utilization patients (frequent emergency or inpatient visits) are precisely the high-risk cohort targeted for clinical intervention. <br>*Chose 2:* Retains crucial risk signal while controlling influence via median-and-IQR scaling. | Boxplot grid (`outlier_boxplots.png`) shows expected long tails in utilization. |
| **Step 9: Feature Engineering** | Historical Healthcare Utilization | 1) Individual visit counts only. <br>2) Create combined `total_visits`. | **Create `total_visits`** | *Rejected 1:* Misses the cumulative healthcare burden of high utilizers. <br>*Chose 2:* Strong holistic predictor of patient frailty and chronic bounce-backs. | `total_visits = number_outpatient + number_emergency + number_inpatient`. |
| **Step 9: Feature Engineering** | Treatment Intensity Metrics | 1) Rely purely on `time_in_hospital`. <br>2) Compute `meds_per_day` and `lab_tests_per_day`. | **Create `meds_per_day` & `lab_tests_per_day`** | *Rejected 1:* Raw medication counts are confounded by length of hospital stay. <br>*Chose 2:* Captures daily clinical management intensity independent of duration. | Ratios computed per hospital day. |
| **Step 9: Feature Engineering** | Polypharmacy & Medication Regimen Stability | 1) Keep individual rare drugs. <br>2) Synthesize `num_active_drugs` and `num_drug_changes`. | **Create aggregate drug indicators; drop 7 component columns** | *Rejected 1:* High multicollinearity and extreme sparsity across individual rare drugs. <br>*Chose 2:* Direct representation of clinical polypharmacy and treatment adjustments; retains `insulin` separately. | Dropped 7 individual drug columns; retained aggregate indicators and raw `insulin`. |
| **Step 9: Feature Engineering** | ICD-9 Clinical Grouping | 1) One-hot encode 700+ raw ICD-9 codes. <br>2) Map into 9 established clinical clusters. | **Map diagnoses into 9 clinical categories** | *Rejected 1:* Exploding dimensionality and extreme sparsity. <br>*Chose 2:* Standard medical clustering (Circulatory, Respiratory, Digestive, Diabetes, Injury, Musculoskeletal, Genitourinary, Neoplasms, Other). | Mapped across `diag_1`, `diag_2`, `diag_3`. |
| **Step 9: Feature Engineering** | Administrative ID Consolidation | 1) Leave 30+ raw administrative IDs as categories. <br>2) Consolidate into meaningful operational groups. | **Group into clinical/administrative clusters** | *Rejected 1:* Overfits rare discharge and admission routes. <br>*Chose 2:* Clusters discharge to (Home, Facility, Home_Health, Other) and admission to (Emergency_Room, Referral, Transfer, Other). | Clear clinical triage alignment. |
| **Step 10: Categorical Encoding** | Nominals vs. Ordinal / Binary Features | 1) One-hot encode all categorical columns. <br>2) `OrdinalEncoder` for ordered/binary; `OneHotEncoder` for nominals. | **Mixed encoding: `OrdinalEncoder` (6) + `OneHotEncoder` (9)** | *Rejected 1:* Creates unnecessarily wide, sparse matrix (98+ columns). <br>*Chose 2:* Maps binary/ordered features (`gender`, `change`, `diabetesMed`, `max_glu_serum`, `A1Cresult`, `insulin`) via integer ranks and nominals via OHE (`handle_unknown='ignore'`). | Keeps feature space compact at exactly 86 features. |
| **Step 10: Numeric Scaling** | Outlier-Resistant Numerical Scaling | 1) Standard `StandardScaler` (z-score). <br>2) `RobustScaler` (median & IQR). | **`RobustScaler`** | *Rejected 1:* Mean and standard deviation are heavily distorted by extreme hospitalization outliers. <br>*Chose 2:* Scales continuous features by the interquartile range, preserving relative distance without outlier collapse. | 14 continuous features scaled; max absolute values post-scaling $\le 6.76$ (`before_after_scaling.png`). |
| **Step 10: Preprocessing Pipeline** | Pipeline Packaging & Leakage Prevention | 1) Ad-hoc Pandas script transformations. <br>2) Scikit-learn `ColumnTransformer` & serialized pipeline. | **Scikit-learn `ColumnTransformer` + `joblib` pickle** | *Rejected 1:* High risk of train-to-test leakage and inference schema mismatch. <br>*Chose 2:* Fit strictly on `X_train`; applied to `X_test`; saved as `preprocessing_pipeline.pkl`. | Complete reproducible pipeline exported to `dataset_processed/`. |
| **Validation Step** | Pipeline Output Verification | 1) Manual spot-checks. <br>2) Programmatic validation suite. | **Automated Validation Report** | *Rejected 1:* Silent bugs or data leakage can pass unnoticed. <br>*Chose 2:* Verifies shapes `(78331, 86)` and `(19491, 86)`, zero missing values, zero leaked IDs, and valid scaling. | All validation tests report PASS. |
| **Step 11: Class Imbalance** | Positive Class Handling (~11.5% Acute Readmission) | 1) Random undersampling of majority class. <br>2) Algorithmic weighting (`class_weight='balanced'`). <br>3) Resampling on training split only (SMOTE). | **`class_weight='balanced'` in model constructors** | *Rejected 1:* Discards >50,000 viable negative patient encounters. <br>*Chose 2:* Algorithmic loss penalty cleanly addresses class imbalance without discarding data. Resampling code provided commented for optional CV testing. | $y_{train}$: 69,327 (0) vs. 9,004 (1); $y_{test}$: 17,288 (0) vs. 2,203 (1) (`final_class_balance.png`). |
